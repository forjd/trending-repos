# trending-repos

A Cloudflare Worker that scrapes [github.com/trending](https://github.com/trending) every 4 hours and serves it as a styled page.

- **Live:** https://trending.ddewhurst.com (also https://trending-repos.danjdewhurst.workers.dev)
- **Repo:** `forjd/trending-repos` (public, MIT)
- **Deploys:** automatic. Merging a PR into `main` deploys it to production (see Deploying)

## How it works

```
cron (0 */4 * * *) or POST /__refresh
  → scrape github.com/trending (HTMLRewriter)
  → refuse to publish if it looks broken (< 5 repos, or no stars-today counts)
  → enrich each repo via GitHub REST API (id, topics, homepage, exact counts)
  → append rows to D1 (history), read back badge stats
  → write the snapshot to KV under "latest", unless KV already has a newer one
  → cron only: ping HEALTHCHECK_URL, or <url>/fail if the scrape or the D1 write failed

GET /              → HTML rendered from KV
GET /api/trending  → the KV snapshot as JSON
GET /fonts/*       → static assets from public/, served before the Worker runs
```

Page loads read only KV. D1 is written and queried only during a scrape.

If D1 fails, the scrape is still published without badges. `/__refresh` then returns `"history": "failed: ..."`, and the cron run fails after it publishes.

| `.github/workflows/deploy.yml` | Deploy workflow: runs on every push to `main` (see Deploying) |

## Commands

| Command | What it does |
|---|---|
| `npm run dev` | Local server on :8787 with local KV and D1. Trigger a scrape with `curl localhost:8787/__scheduled` |
| `npm run typecheck` | `tsc --noEmit` (includes `test/`) |
| `npm test` | Vitest in the Workers runtime, with local KV and D1 and migrations applied. `fetch` is mocked, so no network |
| `npm run types` | Regenerate `worker-configuration.d.ts`. Secret names come from `.dev.vars`, so it must list `GITHUB_TOKEN`, `HEALTHCHECK_URL` and `REFRESH_KEY` (empty values are fine) |
| `npm run db:migrate:local` | Apply migrations to the local D1 |
| `npm run db:migrate` | Apply migrations to production D1 |
| `npm run og` | Regenerate `public/og.png` from `scripts/og-image.html`. Needs `google-chrome` on `PATH`, as on the VM |
| `npm run deploy` | Apply pending D1 migrations to production, then deploy to Cloudflare |

Query production history: `npx wrangler d1 execute trending-repos --remote --command "SELECT ..."`

## Deploying

Every push to `main` (so every merged PR) runs `.github/workflows/deploy.yml`: typecheck, tests, then `npm run deploy`. Pushes that change only Markdown or `LICENSE` skip it. So a docs-only push does not retry a failed deploy. You can also run it by hand from the Actions tab, or with `gh workflow run deploy.yml`. Only runs on `main` can deploy: the job uses the `production` environment, which accepts the `main` branch only.

The workflow reads `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` from GitHub secrets. The token needs Workers Scripts, Workers KV and D1 edit on the account, and Workers Routes edit on the `ddewhurst.com` zone.

To deploy from the `ai-agent` VM, run `npm run deploy`. It applies new migrations before it deploys. Never run `wrangler deploy` on its own: on 2026-10-06 code that needed migration 0003 went out without it, and every history write failed for 26 days. Deploys use the wrangler OAuth login stored in `~/.config/.wrangler`. If the login has expired, run `npx wrangler login --browser=false`, send Dan the URL, and have him paste back the `localhost:8976/oauth/callback?...` URL his browser fails to load. Then `curl` that URL on the VM, using `[::1]` as the host.

After a deploy that changes data shape, run a scrape so KV picks it up:

```
curl -X POST -H "authorization: Bearer $(grep '^REFRESH_KEY=' .dev.vars | cut -d= -f2-)" \
  https://trending.ddewhurst.com/__refresh
```

A new version takes a few seconds to reach every location. A 404 from `/__refresh` right after deploying usually means the old version answered, so retry.

## Secrets

| Name | Where | Notes |
|---|---|---|
| `REFRESH_KEY` | Worker secret, and `.dev.vars` locally | Guards `POST /__refresh` |
| `GITHUB_TOKEN` | Worker secret, and `.dev.vars` locally | Optional. Use a fine-grained token with public read-only access and no permissions. Without it, API lookups are unauthenticated (60/hour, shared with other Workers on the same IP), so most repos miss topics and ids. The page still works |
| `HEALTHCHECK_URL` | Worker secret | Optional. A Healthchecks.io ping URL (4-hour period). Each cron run pings it, or `<url>/fail` with the error. A run skipped by the one-hour guard reports the last scrape instead: success if it saved history, `/fail` if not |

`.dev.vars` and `.env` are gitignored. Never commit or print their values.

## Data

D1 table `snapshot_repos`: one row per repo per scrape, primary key `(fetched_at, rank)`. History starts on 2026-10-05. It has a gap from 2026-10-06 07:18 UTC to 2026-11-01, when migration 0003 was missing in production.

D1 table `repo_days`: one row per repo per UTC day it trended (owner and name compare ignoring case). Badge stats read this, not `snapshot_repos`, so their cost grows with days trending rather than with scrape count. Free-plan D1 allows 5M rows read a day.

A past row is the same repo if its `repo_id` (GitHub's numeric id, so it survives renames) matches, or its owner and name match ignoring case. `repo_id` is NULL for rows saved before migration 0002, or when the API lookup failed.

Badges are computed at scrape time and stored on each `Repo` in the snapshot:

- `isNew`: first seen today (UTC), and only when a scrape was saved yesterday. Otherwise every repo would be "new" on the first day of history, or after a gap.
- `daysTrending`: distinct UTC days seen, not necessarily in a row. The page shows it in the "Days on" column (screen readers hear "Trended on N days"), and sets runs of 7 days or more heavier.

## Gotchas

- **Merging to `main` changes production.** The deploy workflow applies new D1 migrations, then deploys the Worker. The old Worker runs against the new schema for a short time, so make migrations additive. The workflow does not run a scrape, so refresh by hand after a change to data shape.
- **The scraper depends on GitHub's HTML** (`article.Box-row` and children). If GitHub changes it, `refresh()` throws and keeps the old data: `/__refresh` returns 502 and the cron run shows as failed in the dashboard. Check the selectors in `src/scrape.ts` first, then refresh `test/fixtures/trending.html`.
- **Enrichment stops at the first rate-limit response.** The remaining repos keep their scraped data.
- **Bump `wrangler` and `@cloudflare/vitest-plugin` together.** They release in step, and the plugin pins exact wrangler and miniflare versions. Check `npm ls wrangler miniflare` shows one copy of each. If they differ, add `overrides` for the plugin. (`@cloudflare/vitest-pool-workers` is the plugin's old, deprecated name.)
- **`src/index.ts` must export only the default handler.** workerd rejects any other export that isn't an entrypoint (for example `export const X = 1`), so `wrangler dev` fails and a deploy may too. Tests don't catch this; put helpers in their own modules.
- **Cloudflare weakens ETags when it compresses a response** (`"x"` becomes `W/"x"`), so `If-None-Match` comes back weak. `etagMatches()` ignores the `W/` prefix.
- **Link preview tags use absolute URLs on `SITE_URL`** (`src/render.ts`), also on workers.dev. Change it if the domain changes. Sharing sites cache previews, so a new `og.png` can take days to show.
- **Fonts are self-hosted** in `public/fonts` and cached for a year as immutable. To change a font file, give it a new name (the names carry the upstream version) and update `src/render.ts`.
- **Cron changes can take hours to apply, or not apply at all.** On 2026-10-05 a test `* * * * *` schedule kept firing for over 10 hours after it was replaced, and burned through D1's daily read limit. Check what's actually firing with the GraphQL `workersInvocationsScheduled` dataset, not the schedules API, which showed the new schedule the whole time. To fix it, `PUT` an empty schedule list to `/workers/scripts/trending-repos/schedules`, then the real one. As a guard, `scheduled()` skips any run within an hour of the last scrape. Use `/__refresh` to scrape sooner.
- **Changing `database_id` gives you a fresh local D1.** Run `npm run db:migrate:local` again.
- **Local dev is subject to the GitHub API's 60-request hourly limit** without a token. Repeated test scrapes hit it quickly, and enrichment then returns 403s. That's expected, and repos keep their scraped data.
- **Killing dev servers:** `pkill -f wrangler` also matches the shell running it if the command line contains "wrangler". Use `pkill -x workerd` or stop the background task.
- **To preview on the VM**, use Tailscale Serve (`tailscale serve --bg --https=8787 http://127.0.0.1:8787`), not localhost links. Turn it off afterwards.
